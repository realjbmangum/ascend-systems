## ⚠️ xAI VOICE AGENT — everything that cost us hours tonight

Read this before wiring another agent. Almost none of it is documented.

**1. The console has NO field for a bearer token.** It offers only OAuth client
credentials. A header-authenticated MCP server cannot be configured there at
all. Workaround: token in the path — `/api/mcp/t/<token>`.

**2. `WWW-Authenticate: Bearer` on a 401 triggers OAuth discovery.** Under the
MCP spec that header IS an OAuth challenge. The console probes, sees it, and
demands an OAuth app that does not exist. Remove the header.

**3. Answering 405 on GET breaks it.** xAI supports "Streaming HTTP and SSE"
only. The MCP spec permits 405 for a server that never pushes, but a client that
opens the SSE leg first and gets 405 concludes the endpoint is unusable — and in
a console whose only auth UI is OAuth, "unusable" renders as "requires OAuth".
GET must return a real `text/event-stream`.

**4. 🔴 THE BIG ONE — xAI does not give an agent its MCP tools directly.**
They sit behind a `search_connected_tools` meta-tool. The agent must FIND a tool
before it can call it. **The description is the search index, not documentation.**
`create_lead`'s description read "Silently record the caller..." and never
contained the word "lead" — it was invisible. `check_availability` said "open
appointment slots" and was the ONLY tool that ever fired, across three prompt
rewrites. Even after rewriting all six descriptions as search bait, the agent
still failed to find most of them.
**Fix: stop using MCP for tools. Use the console's native "API request" tool
type**, which attaches directly to the agent alongside end_call/web_search with
no search layer. `POST /api/voice/t/<token>/<tool_name>`. Same handlers, same
auth, same tenant routing — a second door, not a fork. This is what finally worked.

**5. A tool schema is a script for what the agent will ask a HUMAN.** `create_lead`
exposed `call_id` — something a voice model cannot possibly know — so it asked
the caller for it, out loud, mid-call. Any field the model cannot fill from
ordinary speech becomes an interrogation. Expose only what a person says out loud.

**6. "Never let the caller learn a tool exists" made it deny having tools.**
Asked directly, the agent said it had no create_lead — obeying literally, and
rationalising a refusal to act as a missing capability. The rule must cover
NARRATION only: use tools constantly, describe the RESULT, never the call.

**7. Wrong base URL fails SILENTLY.** An API-request tool pointed at
`/api/mcp/t/<token>/create_lead` matched no route, fell through to the admin auth
gate, returned a bare 401 — and the agent swallowed it. The call sounded perfect,
the caller was told their details were taken, nothing was written. This is the
silent-capture failure arriving through a config typo. `/api/mcp/t/:token/:tool`
now returns a 404 that names the mistake and gives the correct URL.

**8. Log SUCCESSES, not just failures.** We could not tell a working agent from
one that handshakes and never acts until `[mcp] ... tools/call X OK` existed.
Without it, "connected" and "broken" look identical from the server side.

**9. Teams are funded separately.** Each xAI team carries its own prepaid credit
balance. A balance at zero is a dead phone line for that client. No alerting
exists. This is failure domain F3 in the SOP.

## Session - July 25, 2026 — OAuth MCP, department agents, and the repo decision

**Shipped:**

  discovery (RFC 8414), protected-resource metadata (RFC 9728) and dynamic
  client registration (RFC 7591). The consent screen is an AGENT PICKER, and the

- **Demo board** at `/demo/phone`: 5 stat tiles, a 7-day chart, jobs-by-status,

## DECISION — one repo, N tenants. NOT one repo per client.

Brian's mental model at 10 clients was: 10 D1s, 10 xAI teams, 10 agent setups,
**10 git repos**, 10 websites, 10 back-office products.

Everything on that list is right except the repos, and that one would undo the
multi-tenant work. `db_binding` is what makes one Worker serve every tenant.
The cross-customer leak in `get_work_orders` took ONE commit to fix; across ten
repos it would have been ten PRs and one of them would have been missed.

The line:
- **Platform — one repo.** Worker, tools, health checks, admin. Client eleven
  touches zero code.
- **Per-client — data, not code.** A D1, an xAI team, rows in `voice_agents`,
  five KB files. Onboarding is a checklist.
- **Bespoke — its own repo, and only at Tier 3** ($7.5–15k build), when a client
  genuinely needs their own system written into. Same rule that makes Sightline
  and Crown and Compass separate today.

At 10 voice clients: **1 repo, 10 databases, 10 teams, ~40 config rows.**

Also: websites and back-office builds are SEPARATE service lines wearing the same
client list, not part of the voice platform. Ten voice clients might yield two
back-office builds — and those two are where the $15–50k lives.
